nimplex build plan

Map Omnara's architecture to Cloudflare: what the platform replaces, what becomes an existing primitive, what remains ours to build, and in what order.

2026-08-23 · Based on Omnara's 450,000-line source review, the computer/Think/Flue articles, and the then-approved Cloudflare-first, frontend-first, contracts-first decisions. Later runtime decisions supersede this plan.

The Map

One map: what happens to each Omnara component

Omnara built four layers in roughly 450,000 lines of Go including tests. Rebuilding on Cloudflare, roughly 70% of the effort disappears or becomes platform primitives ; the remaining 30% is the product layer customers pay for.

What You Build

Five things we actually build

  • Contracts: the foundation : promote packages/contracts to the wire specification. Every resource includes end_user scope and every run carries budget fields from day one. Keep Cloudflare types out.
  • Console: in progress : end-user usage, SSE run timelines, approvals, budgets/caps, and credentials. Start with mocks.
  • Runtime: apps/runtime, one Wrangler project : one DO per user/session with Think, computer Workspace, and tools. Model/tool calls pass metering, permission, and credential checks before admission. Exhausted budget stops execution inside the DO.
  • Two end-user SDKs : Server SDK uses org keys to create sessions/issue tokens; Client SDK uses short-lived user tokens. Generate from contracts, then refine developer experience.
  • Native product tool bridge : reuse Omnara's custom-tool shape, mark tools ready, and submit external results through SubmitToolCallResult so customers can expose their product's functions as agent tools.

Sequence

Recommended build order

Each phase has an acceptance statement. Prioritize sequence over fixed dates for a solo project.

P0

Contracts and mock server Start here

Define end_user/session/run/budget/credential/tool-policy with Zod/OpenAPI; serve conforming mock data through an in-memory Hono server.

Acceptance: Console and runtime import only contracts; switching base URL selects mock or real backend.

P1

Console application logic Current task

Build run timelines, user usage/caps, allow/ask/deny approvals, and credentials against mocks; use them for product validation too.

Acceptance: Mock data demonstrates user initiation, spending, budget exhaustion, and approval.

P2

Minimal working runtime

One DO agent, computer Workspace, two or three exec/web tools, and SSE back to console. Begin with simple usage counting and immediate budget stops.

Acceptance: Replace the mock without changing console code; an active run stops when its fake budget is exhausted.

P3

Implement the three enforcement checks

Durable ask approvals resume even the next day; inject per-user credentials outside model context; define and enforce application-level egress allowlists.

Acceptance: An unauthorized tool waits in the inbox and resumes from the interruption after approval.

P4

SDK and open-source delivery

Package both SDKs, an embedded customer-app example, README, and deploy-to-your-Cloudflare-account guide.

Acceptance: A new developer runs an end-user agent in their app within thirty minutes using the README.

Guardrails

Boundaries and exclusions

computer is early preview. Keep its API inside apps/runtime and out of contracts so upgrades affect one directory.
Cloudflare is moving up the stack ; Flue is the first consumer. Speed and depth of end-user primitives are the defense; work outside P0–P4 distracts from it.
Excluded: Generic management competing with AI Gateway, desktop GUI computer use beyond a beta flag, Slack integrations, Phase 2 marketplace, and BYO machines.
