2026-08-24 · Historical product blueprint

Ten ideas, organized into one design

The original framing was Vercel for agents. This presentation refines each idea and identifies unresolved contradictions; later architecture decisions supersede it.

Overall architecture

SDK supplies execution; Console supplies policy

From installation to managed execution

Refining the ten ideas

Build directly or revise first

#1 #2

Configure before login

Original request: configure the SDK, then sign in to Console

Treat the sequence as: login is an upgrade, not the entry point . After installation, a developer npm install should not have to register before trying the product.

Recommendation One interface, two backends: localGovernor() local configuration and in-memory counters; hostedGovernor() a remote service. Shared versus local operation is the distinction, following LiteLLM/Langfuse/Sentry.

#3

App、preview URL、worktree branching

Original request: one sandbox-service URL with branched configuration versions

Clarify the resource being previewed: a preview represents agent configuration, not application source . Branch harness choice, provider, skills, and policies.

Recommendation Put nimplex.toml in Git to reuse versioning. Branch, preview environment, and local worktree map one-to-one.

#4

TOML configuration and secrets

Original request: TOML synchronizes cloud settings and environment secrets

The main risk is an ambiguous source of truth and configuration drift when both sides edit the same data.

  • nimplex.toml Version-controlled declarative configuration is authoritative
  • secret Store only references （{{ secret.OPENAI_KEY }} ); secret values live in the cloud vault and never enter Git
  • Console edits non-versioned data: secret values, budgets, and RBAC

Recommendation Keep Git configuration and vault values separate. Console configuration becomes read-only, showing its source main branch.

#5

RBAC, anonymous users, per-user usage

Original request: RBAC, anonymous users, and per-user token allocation

These are separate concerns with different complexity and value:

  • Team RBAC controls which customer employees edit configuration; reuse existing providers, avoid building it from scratch , and consider Clerk/WorkOS
  • End-user budgets control customer-user spending; this proposal's primary differentiation and implementation priority
  • Anonymous users use device/IP hashes with small fixed caps for abuse prevention

MVP Begin with end-user budgets and owner/member team roles. Model usage through a few fixed plans rather than an arbitrary rules engine.

#6

CLI push skills、agents、MCP

Original request: define locally and push through CLI

One adoption decision matters: reuse existing formats 。

  • .claude/skills/*/SKILL.md : Claude Code's existing format
  • AGENTS.md : Codex's existing format
  • .mcp.json : MCP server configuration

Recommendation nimplex push Package existing directories without migration. Skills follow branches so preview changes cannot alter production skills.

#7

Local execution through Docker

Original request: the agent SDK should run locally, possibly through Docker

This complements the first idea. The key is dev / prod parity that local and cloud read the same TOML with different providers.

Recommendation nimplex dev Start the complete local environment with Docker, a SQLite governor, and local traces/UI. Cloud migration should preserve application configuration.

#8

Trace view and conversational analysis

Original request: execution trajectories/statistics with an analysis conversation

Conversational analysis is a query interface; it depends on a sound data model . Each trace is a tree:

run → step( model call | tool call | sandbox exec )

Every node includes cost、tokens、duration、end_user_id、outcome . Without end_user_id , queries cannot identify the highest-spending users.

Recommendation Use OpenTelemetry GenAI semantic conventions rather than custom fields, enabling export to Langfuse/Datadog and retaining customer data portability.

#9

Cron and webhook triggers

Original request: cron/webhook agent triggers

One question can break the budget model : who owns a cron-triggered run when no end user initiated it?

Recommendation Introduce a service identity early, with its own budget and kill switch. Webhook payloads must map to end_user_id for tenant-aware cost attribution.

#10

Customer Claude Code / Codex OAuth

Original request: users sign in to Codex or Claude Code and use subscription OAuth for agent execution

Customer-owned subscriptions may reduce the platform's token costs , but three issues need resolution:

  • Terms of service : verify whether server-side automation through subscription tokens is permitted; do not assume it
  • High-value credential custody requires vault protection, revocation, and audit and creates an attractive target
  • Conflict with the budget feature , explained next

Recommendation Expose distinct credential modes and explain their actual enforcement differences.

Contradictions to resolve

Subscription access undermines USD enforcement

The desired subscription feature conflicts with the proposed budget differentiator.

Branch in, preview out

Idea 11 · Added later

Pause and resume

Beyond convenience, this can become a stronger budget-control experience 。

Why it matters

Make budget exhaustion a resumable product event

A basic kill switch offers only continue or kill. Destructive termination can lose progress and create avoidable customer frustration.

Pause provides a third option: stop at the cap, then continue after a budget increase.

Result The same checkpoint mechanism turns a terminal interruption into a continuation opportunity.

Implementation

Extend checkpoint responses from boolean to an enum

{ action: 'continue' | 'pause' | 'stop' | 'await_approval' }

After the SDK receives pause , perform the following sequence:

  • Call the harness's doSuspendTurn() and obtain ContinueTurnState as required by the proposed adapter contract
  • Store that state in the control plane
  • Ask the provider to pause or snapshot the sandbox

Resume in reverse: resumeSession() restore the sandbox → doStart({ resumeFrom }) reconnect → doContinueTurn() continue from the checkpoint.

Benefit Pause, stop, and approvals share one request/response mechanism.

Difficulty

Provider support differs and the reviewed interface is incomplete

The interface-level HarnessV1SandboxProvider provides only createSession and optional resumeSession? —— without a pause verb . Define the additional operation and negotiate capabilities explicitly.

  • Native support, such as DO hibernation or E2B pause, can preserve the environment cheaply
  • Otherwise save workspace files, destroy the sandbox, and reconstruct on continuation

Fallback preserves files, not an arbitrary running process. An active npm install may disappear, while files and conversation survive through the harness's ContinueTurnState state outside the sandbox.

Required boundary Never silently turn a Pause button into destructive termination. Explain when a provider supports only stop-and-restart.

Remember

Paused does not mean free

Snapshots occupy billable storage; make those charges visible.

Recommendation Show paused storage separately and apply TTLs with expiry notifications so forgotten snapshots do not accumulate indefinitely.

Missing from the original ten ideas

Four additions

Addition A

Kill switch for active runs

Console needs a control that actually interrupts execution. The proposed distinction from admission-only gateways is checking inside the harness/tool loop, rather than only denying the next model request; the original design targeted sub-second checks.

However, kill is the basic version; pause is the more useful continuation feature , as discussed above.

Addition B

Pending approvals

The agent wants to execute rm -rf , send an email, or make a payment: allow it? Vercel's HarnessV1PendingToolApproval already models the request; Console supplies an inbox. The proposal treats this as an enterprise requirement and potential paid feature.

Addition C

Egress policy configuration

Network allowlists need an editor. The reviewed interface ( HarnessV1NetworkPolicy ) already defines allow-all / deny-all / custom three modes plus host/CIDR lists; supply UI and persistence rather than another schema.

Addition D

Cost attribution reports

Traces inspect individual executions; reports aggregate spending by app, end user, and tool. This is the proposed recurring management view.

Most listed features already existed elsewhere in the reviewed ecosystem.
The proposal centers on controlling active runs: continue, pause, and terminate.
The MVP should demonstrate that behavior, with other features supporting it. Later nimplex decisions refine this historical scope.
