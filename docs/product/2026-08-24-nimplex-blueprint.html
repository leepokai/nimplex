整體架構

SDK 做「做得到的事」，Console 做「說了算的事」

使用者旅程

從安裝到管起來

注意第 1、2 步的順序 —— 能跑起來在前，註冊在後。

01
npx nimplex init

產生 nimplex.toml。不需要帳號。

02
nimplex dev

本機 Docker 當 sandbox、SQLite 當預算計數器、trace 寫本機檔。功能完整，只是不共享。

03
登入 console

發生在他需要「多人共享」或「上線」的時候，不是第一天。

04
建立 App

一個 App = 一組 agent 設定的家。綁一個 git repo。

05
nimplex push

把 skills、MCP 設定、secret 推上去。設定走 git，secret 走 vault。

06
開 branch → 自動長出 preview

每條 branch 一個獨立環境：獨立設定、獨立 secret scope、獨立預算。

07
接 trigger

cron、webhook、或你的應用程式直接呼叫 SDK。

08
在 Trace tab 看、在 Console 管

看軌跡與花費；超標自動停、也能手動按紅色按鈕殺掉跑到一半的 run。

你的十點 · 逐項細化

哪些直接做，哪些要先改一下

#1 #2

先 configure，再登入

你說的：使用 SDK configure 好之後，登入到 console

順序要反過來想：登入不能是入口，只能是升級。開發者 npm install 之後如果第一件事是註冊拿 key，採用率會直接歸零。

建議 同一組介面、兩種後端：localGovernor() 讀設定檔、記憶體計數；hostedGovernor() 指向你的服務。功能一模一樣，差別只在「共不共享」。LiteLLM、Langfuse、Sentry 全是這個形狀。

#3

App、preview URL、worktree branching

你說的：sandbox service 對應一個 URL，可以 branch 出很多不同的 sandbox configure version

直覺是對的，但要先釘死一件事：preview 對應的是「一組 agent 設定」，不是「一份程式碼」。你要 branch 的是 harness 選擇、sandbox provider、skills、政策 —— 不是應用程式原始碼。

建議 把 nimplex.toml 放進 git，branching 就自動成立，不用另外設計一套版本機制。git branch ↔ preview 環境 ↔ 本機 worktree，三者一一對應，心智模型跟 Vercel 完全一致，使用者不用學新東西。

#4

TOML 同步設定與 secret

你說的：需要一個 toml 檔案同步雲端設定和雲端 env secret

這裡最容易出事的是 source of truth 不明 —— 兩邊都能改就會 config drift。

  • nimplex.toml 進版控，是宣告式的、唯一的設定來源
  • secret 只留引用（{{ secret.OPENAI_KEY }}），值存在雲端 vault，永遠不進 git
  • Console 只能改「不該進版控的東西」：secret 值、預算、RBAC

建議 設定歸 git，secret 歸 vault，界線畫死。Console 上的設定頁改成唯讀＋「這是從 main 分支讀來的」。

#5

RBAC、匿名 user、每人用量

你說的：RBAC 設定、匿名 user 設定、每個 user 對應多少 token 使用量

你把三種不同的東西混在一起了，它們的難度和價值差很多：

  • 團隊 RBAC（你客戶的員工誰能改設定）—— 零差異化，別自建，用 Clerk / WorkOS
  • End-user 額度（你客戶的使用者，每人多少 $）—— 這才是護城河，全力做
  • 匿名 user（未登入的 end-user）—— 用 device / IP 雜湊當身分，給極小固定額度，本質是防濫用

MVP 只做 end-user 額度，團隊權限先給 owner / member 兩級。「搭配 DB 給不同 user 不同用量」先抽象成幾個固定 plan，別一開始就做任意規則引擎。

#6

CLI push skills、agents、MCP

你說的：user 在 local 自定義完，透過 CLI push 上來

這點很好，但有個決定會影響採用率：不要自創格式。

  • .claude/skills/*/SKILL.md —— Claude Code 現有格式
  • AGENTS.md —— Codex 現有格式
  • .mcp.json —— MCP server 設定

建議 nimplex push 直接掃這些既有目錄打包上傳。使用者手上的 skills 零遷移成本就能用 —— 這會是很強的採用理由。另外 skills 要跟著 branch 走，preview 的 skills 不能污染 production。

#7

本機可跑，用 Docker

你說的：agent SDK 要在 local 可跑，可能有 docker 處理

這跟 #1 是同一件事的兩面。關鍵是 dev / prod parity：本機和雲端讀同一份 TOML，只是 provider 不同。

建議 nimplex dev 起完整本機環境：sandbox 走 Docker provider、governor 走 SQLite、trace 走本機檔＋本機 UI。使用者換到雲端時一行設定都不用改。

#8

Trace tab 與分析對話

你說的：每個 agent 的運行軌跡和統計數字，提供使用者做分析對話

「分析對話」是好點子，但它是查詢介面 —— 資料結構做對了它才有東西可查。一條 trace 是一棵樹：

run → step( model call | tool call | sandbox exec )

每個節點都要帶 cost、tokens、duration、end_user_id、outcome。少了 end_user_id，「誰花最多錢」就永遠查不出來。

建議 直接用 OpenTelemetry 的 GenAI semantic conventions，別自創欄位。好處是使用者可以同時把 trace 匯出到 Langfuse / Datadog —— 「不綁架你的資料」本身就是賣點。

#9

Cron、webhook 觸發

你說的：提供 cron、webhook 等 trigger agent 的方式

這裡藏著一個會打破你整個預算模型的問題：cron 觸發的 run，算在誰頭上？它沒有 end-user。

建議 早點引入 service identity（系統身分） 的概念 —— 它也是一個 principal，有自己的預算和 kill-switch。webhook 則必須能從 payload 映射出 end_user_id，否則多租戶的成本歸因會整段斷掉。這個決定越晚做越痛。

#10

讓 user 用自己的 Claude Code / Codex OAuth token

你說的：讓 user 能夠登入 codex 或 claude code，使用 oauth token 來 serve user

價值很高：使用者用自己的訂閱，你完全不承擔 token 成本 —— 這解掉 agent 產品最大的一塊成本。但有三件事必須先面對：

  • ToS 風險 —— 拿訂閱制的 OAuth token 跑伺服器端自動化，是否違反供應商條款，要去查清楚，不能假設沒事
  • 你會持有高價值憑證 —— 需要 vault 等級保護、可撤銷、可稽核。這是你整個系統最值得被攻擊的地方
  • 它跟 #5 直接衝突 —— 見下一節

建議 做成兩種 credential 模式並存，並在 UI 上明講差別，不要讓使用者以為兩邊一樣。

#11 · 後來補的

暫停與重啟

這條表面上是便利功能，實際上是你護城河的更好版本。

為什麼重要

把「預算超標」從破壞性事件變成商業事件

你現在的 kill-switch 是二選一：讓它跑，或殺掉。殺掉會丟掉所有進度 —— 對使用者是純粹的損失，對你是純粹的客訴。

暫停給了第三個選項：預算用完時暫停，使用者加值後從斷點續跑。

結果 同一個機制，從「懲罰」變成「收錢的時機」。這比 kill-switch 好得多，而且是同一套 checkpoint 通道就能做到的。

怎麼做

不需要新的子系統，只要把 checkpoint 的回應從布林改成 enum

{ action: 'continue' | 'pause' | 'stop' | 'await_approval' }

SDK 收到 pause 之後的動作序列：

  • 呼叫 harness 的 doSuspendTurn()，拿到 ContinueTurnState（規格保證每個 adapter 都有）
  • 把那份 state 存進 Console
  • 叫 provider 對 sandbox 做 pause 或 snapshot

續跑就是反過來：resumeSession() 還原 sandbox → doStart({ resumeFrom }) 重連 → doContinueTurn() 從斷點跑下去。

好處 pause、stop、審批全部共用同一條往返，不用為每個功能各拉一套機制。

難處

provider 支援度不一，而且沒有規格可靠

規格層的 HarnessV1SandboxProvider 只有 createSession 和可選的 resumeSession? —— 沒有 pause 動詞。你等於要自己定義第三個動詞，並且做能力協商。

  • 底層原生支援（Cloudflare DO 本來就會 hibernate、E2B 有 pause）→ 真暫停，幾乎免費
  • 不支援 → 降級：存下 workspace 檔案 → 銷毀 sandbox → 續跑時重建並還原

降級版的物理極限：檔案可以搬，跑到一半的 process 不能搬。 所以正在跑的 npm install 會消失，但檔案和 agent 的對話狀態都保得住（後者存在 harness 的 ContinueTurnState 裡，跟 sandbox 無關）。

要守的底線 UI 上的暫停鍵，絕對不能在不支援的 provider 上悄悄變成殺掉。能力不足就明講「這個 provider 只能停止並重來」。

別忘了

暫停不等於零成本

snapshot 佔儲存空間，多數 provider 照收。使用者會以為「我暫停了就不用付錢」，然後在帳單上被嚇到。

建議 Console 上把 paused 的儲存費用單獨列出來，並且給每個 paused sandbox 一個 TTL 加到期通知 —— 否則你會養出一堆沒人記得的殭屍 sandbox，成本慢慢流血。

你的十點裡沒有

四件該補進去的事

補 A

Kill-switch：殺掉跑到一半的 run

Console 上要有一顆紅色按鈕，而且它必須真的能中止已經在跑的 agent。這是你相對於 LiteLLM 唯一沒被做掉的差異 —— LiteLLM 只能擋「下一次 model 呼叫」，因為它只在 gateway 那層；你的 SDK 在 harness 迴圈裡面，每個 tool call 都是一個檢查點，停止粒度是次秒級。

但 殺掉只是粗糙版本，暫停才是你真正要賣的東西 —— 見上一節。

補 B

審批佇列（pending approvals）

「這個 agent 想執行 rm -rf / 想寄這封信 / 想付這筆錢 —— 准不准？」Vercel 的 HarnessV1PendingToolApproval 規格裡已經有這個概念，你的 Console 只要提供收件匣。這是企業客戶的剛需，也是很自然的付費理由。

補 C

Egress 政策的設定介面

網路白名單要有地方設。規格層（HarnessV1NetworkPolicy）已經定義好 allow-all / deny-all / custom 三種模式加上 host 與 CIDR 清單 —— 你只要做 UI 和存放，不用自己設計。

補 D

成本歸因報表

Trace 是「一條一條看」，報表是「加總起來看」。per-app、per-end-user、per-tool 的花費排行 —— 這是客戶真正會每週打開的那一頁，也是續訂的理由。

切線建議

MVP 該包含什麼

判準只有一條：先做沒人做過的，後做別人也有的。

階段做什麼為什麼
MVPTOML + CLI push + nimplex dev沒有本機體驗就沒有採用
MVP單一 sandbox provider + 單一 harness多 provider 是加法題，晚點做不影響架構
MVPper-end-user 預算 + checkpoint + kill-switch唯一沒人做的東西，你的全部理由
MVPpause / resume（先做一個原生支援的 provider）「暫停後加值續跑」比「殺掉」好賣太多
MVP基本 trace（樹狀 + 成本欄位）資料結構錯了以後改不動
下一步preview branching · 審批佇列 · egress UI形狀好但不緊急
下一步RBAC · 匿名 user · cron / webhook有現成方案可接
